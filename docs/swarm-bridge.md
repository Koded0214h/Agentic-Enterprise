# Swarm Bridge

The swarm bridge is the integration contract between **Agent Swarm** (execution engine) and **AOS** (control plane). It consists of five HTTP endpoints on the Django side and a thin client library (`core/aos_client.py`) on the swarm side.

---

## How It Works

Every time `orchestrator.py` dispatches an agent, `core/aos_client.py` wraps the execution in three AOS calls:

```
Before execution:
  aos_client.policy_check(execution_id, agent_name, task)
  → POST /api/swarm/policy/check/
  → Returns: allow | deny | escalate

During execution:
  engine.run(agent_definition, task)

After execution:
  aos_client.usage_report(execution_id, tokens, cost, duration)
  → POST /api/swarm/usage/report/

  aos_client.emit_trace(execution_id, phase, event_type, payload)
  → POST /api/swarm/traces/
```

---

## Offline Mode (Fail-Open)

If `AOS_BASE_URL` or `AOS_TOKEN` are not set in `agent-swarm/.env`, the `aos_client` operates in **offline mode**:

```python
ENABLED = bool(_BASE_URL and _TOKEN)

def policy_check(...):
    if not ENABLED:
        return {"decision": "allow"}   # silent no-op
```

This means the swarm will run without governance if AOS is unreachable. This is intentional for development and isolated testing. **Never run in offline mode in production.**

If AOS is configured but temporarily unreachable (network error, timeout), `policy_check` also fails open with a warning:

```
[AOS] Policy check unreachable — proceeding (fail-open)
```

To change this to fail-closed (block on AOS unavailability), edit `core/aos_client.py`:
```python
# Change this line in policy_check():
return {"decision": "allow"}
# to:
return {"decision": "deny", "reason": "AOS unreachable — fail-closed"}
```

## Connection Configuration

`agent-swarm/.env`:
```bash
AOS_BASE_URL=http://localhost:8000   # AOS Django backend URL
AOS_TOKEN=eyJhbGci...               # JWT from POST /api/token/
AOS_ENV=dev                         # dev | staging | prod
```

`start.sh` writes this file automatically with a fresh token on every startup.

**JWT tokens expire** (default: 5 minutes for access tokens). For long-running swarm sessions, either:
- Re-run `start.sh` to get a fresh token, or
- Use `POST /api/token/refresh/` with the refresh token to get a new access token

## SwarmExecutionContext

Every policy check creates a `SwarmExecutionContext` record in AOS. This is the anchor that ties all subsequent calls (usage report, trace events) together.

| Field | Description |
|---|---|
| `id` | The `execution_id` UUID (generated by `aos_client.new_execution_id()`) |
| `aos_agent` | FK to the AOS `Agent` record (resolved via `SwarmAgentManifest`) |
| `swarm_agent_name` | Raw swarm agent name (e.g., `sales-account-strategist`) |
| `engine` | LLM engine used (claude / gemini / generic) |
| `workflow_phase` | Which swarm phase triggered this execution |
| `environment` | dev / staging / prod |
| `task_summary` | First 500 chars of the task |
| `policy_decision` | allow / deny / escalate |
| `policy_reason` | Human-readable reason |
| `tokens_input` | Filled in by `usage_report` |
| `tokens_output` | Filled in by `usage_report` |
| `cost_usd` | Calculated cost |
| `duration_ms` | Wall clock execution time |
| `started_at` | When the context was created |
| `completed_at` | When `usage_report` was received |

## SwarmAgentManifest

The sync command (`python manage.py sync_swarm_agents`) creates one `SwarmAgentManifest` per swarm agent. The manifest links the swarm's name string to an AOS `Agent` record.

This is what allows `POST /api/swarm/policy/check/` to resolve `agent_name: "sales-account-strategist"` to a full `Agent` record with roles, budget, and policy assignments.

If an agent name is not in the manifest, the policy check still runs but with no AOS agent context — it falls back to global policies only.

## Syncing Agents

Run the sync command whenever `swarm.config.json` or agent `.md` files change:

```bash
cd backend
source .venv/bin/activate

# Full sync
python manage.py sync_swarm_agents

# Dry run (see what would change)
python manage.py sync_swarm_agents --dry-run

# Sync only one category
python manage.py sync_swarm_agents --category engineering
```

The sync command:
1. Reads `swarm.config.json` for the agent list
2. Reads each agent's `.md` file for description and metadata
3. Creates or updates `Agent` + `SwarmAgentManifest` records
4. Is fully idempotent — safe to run as many times as needed

## Budget Enforcement

Before calling `PolicyEvaluator`, the policy check view runs a fast budget check:

```python
if budget.current_month_spend >= budget.monthly_limit:
    decision = "deny"
    reason = f"Budget limit exceeded: ${spend} / ${limit} monthly"
```

This means even a global ALLOW policy cannot override a breached budget. Budget denials are still logged to `PolicyAuditLog`.

To set a budget for a swarm agent:
```bash
curl -X POST http://localhost:8000/api/billing/budgets/ \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "agent": "<agent-uuid>",
    "monthly_limit": "50.00",
    "alert_threshold": "40.00",
    "is_active": true
  }'
```

## Knowledge Base Enrichment

Swarm agents can query the AOS knowledge base before execution to enrich their context:

```python
# In orchestrator.py or agent dispatch logic
context_docs = aos_client.kb_query(
    query=task,
    agent_name=agent_name,
    top_k=5
)
```

This calls `GET /api/swarm/kb/query/` which searches all active `KnowledgeCollection` records using ChromaDB semantic similarity and returns the most relevant document chunks.

## Trace Events

The swarm emits trace events at key lifecycle points:

| Phase | Event type | When |
|---|---|---|
| `execute` | `agent_start` | Agent dispatch begins |
| `execute` | `agent_complete` | Agent returns successfully |
| `debug` | `recovery_attempt` | Self-healer kicks in |
| `debug` | `recovery_success` | Self-healer succeeded |
| `debug` | `recovery_failed` | All recovery strategies exhausted |
| `ship` | `verification_complete` | Delivery verification done |

Each trace event creates a `TraceStep` record in AOS, linked to a `Conversation` (auto-created per `execution_id`). These are queryable at:

```
GET /api/intelligence/conversations/{conv-id}/traces/
```

## Adding the Bridge to Custom Swarm Code

If you write custom orchestration code and want to hook into AOS governance:

```python
from core import aos_client
import time

def my_dispatch(agent_name, task, engine="claude"):
    # 1. Get a fresh execution ID
    execution_id = aos_client.new_execution_id()

    # 2. Policy gate
    policy = aos_client.policy_check(
        execution_id=execution_id,
        agent_name=agent_name,
        task=task,
        engine=engine,
    )
    if policy.get("decision") != "allow":
        print(f"Blocked: {policy.get('reason')}")
        return None

    # 3. Emit start trace
    aos_client.emit_trace(execution_id, agent_name, "execute", "agent_start")

    # 4. Run your agent
    start = time.time()
    result = run_my_agent(agent_name, task)
    elapsed_ms = int((time.time() - start) * 1000)

    # 5. Report usage
    aos_client.usage_report(
        execution_id=execution_id,
        agent_name=agent_name,
        engine=engine,
        duration_ms=elapsed_ms,
        tokens_input=result.get("tokens_input", 0),
        tokens_output=result.get("tokens_output", 0),
        cost_usd=result.get("cost", 0.0),
        success=True,
    )

    # 6. Emit completion trace
    aos_client.emit_trace(execution_id, agent_name, "execute", "agent_complete",
                          payload={"output": result.get("summary")})

    return result
```
